# アーキテクチャ

*[English](architecture.md) | [日本語](architecture.ja.md)*

`board-identify` は 3 つの同一性を区別します。

- **ポート**: `/dev/ttyUSB2` のような、一時的なカーネルノード。
- **トランスポート**: CH340、FTDI、WCH-Link デバッグプローブのような USB インタフェースまたは USB-UART ブリッジ。
- **ターゲット**: トランスポートの先にあるマイコンボード。

1 つのポートに名前を 1 つだけ付けるとは限りません。単なる USB-UART ブリッジ自体には見るべきものがありませんが、デバッグプローブは違います。固有のシリアル番号を持ち、デバッグ端子の先のボードは差し替えられます。そのためプローブは識別結果のリストを、具体的なものから順に返し、その一つ一つが同じポートを指すリンクになります。

パブリッシャは識別結果ごとに `/run/board-identify/by-id/` へアトミックにシンボリックリンクを作成し、その一組を一時的なポート名をキーにして状態として保存します。

## モジュール

| モジュール | 責務 |
| --- | --- |
| `paths` | ランタイムの配置。`by-id/` のリンクと `state/` のファイル。 |
| `model` | プローブ 1 回の結果である `Identification`。 |
| `normalize` | チップ名や固有 ID を安全な構成要素へ正規化する。 |
| `usbinfo` | ポートを開かずに sysfs から読む USB のメタデータ。 |
| `probes/` | ターゲットファミリごとのクラス。`identify_port()` が選択する。 |
| `identify` | プローブの振り分け、`publish()`、`remove_port()`。 |
| `cleanup` | 切断されたデバイスが残したリンクと状態の掃除。 |
| `cli` | `identify`、`remove`、`cleanup` の各サブコマンド。 |

## ランタイムの配置

```text
/run/board-identify/
├── by-id/
│   ├── esp32-s3-7cdfa1123456 -> /dev/ttyUSB2
│   ├── ch32x035c8t6-1ff9abcd880ebc48 -> /dev/ttyACM4
│   └── wch-link-fc928f068181 -> /dev/ttyACM4
└── state/
    ├── ttyACM4.json
    └── ttyUSB2.json
```

リンクはボード、状態ファイルはポートをキーとし、1 つの状態ファイルが複数のリンクを持ちます。

```json
{
  "port": "/dev/ttyACM4",
  "board_ids": [
    "ch32x035c8t6-1ff9abcd880ebc48",
    "wch-link-fc928f068181"
  ],
  "identifications": [ ... ]
}
```

どちらも一時的な名前で書き出してから `os.replace()` で所定の位置へ移動するため、読み手が中途半端なリンクや書きかけの状態ファイルを見ることはありません。

## ライフサイクル

1. udev が新しい `ttyUSB*` / `ttyACM*` ノードを検出し、`board-identify@<port>.service` を起動する。
2. `identify_port()` が各プローブに対応可否を尋ね、対応するものに識別を依頼する。
3. `publish()` が識別結果ごとのリンクと状態ファイルを書き出す。前回は名乗っていたが今回は名乗らなかった名前は先に削除するため、デバッグプローブから外されたターゲットのリンクが残ることはない。
4. デバイスが外れると `BindsTo=` によりユニットが停止され、その `ExecStop=` が `board-identify remove <port>` を実行する。
5. `board-identify cleanup` は、再起動や異常終了などで取り残されたリンクと状態をさらに掃除する。

## デバッグプローブ

デバッグプローブは、自分の先に何が付いているかを知っているトランスポートなので、2 段階で識別します。

1. **ディスクリプタから、常に。** sysfs から VID/PID とシリアル番号が、USB 通信も tty のオープンもなしに取れます。これがプローブ自身の名前になります。この段階は失敗しませんし、何も乱しません。
2. **ターゲットから、指示されたときだけ。** プローブのベンダインタフェースを claim して短いコマンド列を流すと、接続されているチップのシグネチャと工場出荷時の UUID が得られ、これがボードの名前になります。`--no-target-probe` はこの段階を丸ごと省くため、USB 通信はまったく発生しません。

プローブ自身のリンク名をあえてディスクリプタだけから作っているのは意図的です。WCH-Link がベンダインタフェース越しに報告する型名のほうが良い名前ですが、それは既にデバッグセッションがそのインタフェースを掴んでいると取得できません。他に誰が動いているかで変わる名前は、安定した名前ではありません。型名はトランスポートとして記録します。

## 標準の仕組みを使わない理由

`/dev/serial/by-id/`、`/dev/serial/by-path/`、`ATTRS{idVendor}` / `ATTRS{idProduct}` / `ATTRS{serial}` を照合する udev ルールは、使えるなら常にそちらが正解であり、接続時のコストもかかりません。本プロジェクトが扱うのは、その残りの領域です。

- シリアル番号を報告しないアダプタ（多くの CH340 モジュールなど）。`by-id` では複数のボードが 1 つの名前に潰れてしまいます。
- USB/IP で WSL へ転送されたデバイス。Windows 側のバス ID は Linux から見えず、`by-path` は物理的な接続位置ではなく `vhci_hcd` への attach 順を反映します。

どちらの場合も、attach し直しても変わらない識別子はターゲット自身から得るしかありません。プローブが読み取るのはそれです。

## 既知の制約

- ターゲットと通信すれば、ターゲットは乱されます。`esptool` は DTR/RTS を操作してブートローダへ入るので、接続イベントのたびにファームウェアが再起動します。WCH-Link の attach はコアを保持して解放するので、再起動ではなくタイミングの中断になります。いずれにせよ本プロジェクトは開発環境向けのツールであり、環境の安定性が求められる場面には適しません。
- ディスクリプタだけで足りるデバイスもあります。WCH-Link は VID/PID で認識され、`esptool` が走る前にプローブの連鎖が終わります。ただし汎用のディスクリプタ高速パスはまだないため、どのプローブも sysfs で認識できないポートは、いまも通信して識別されます。
- 表を引いてターゲットに名前を付けるため、表に載っていないチップはシリーズ名、あるいは生のシグネチャにフォールバックします。あとで表に追加するとリンク名は変わります。これは attach をまたぐ変化ではなくアップグレードをまたぐ変化です。
- ベンダインタフェースを既にデバッグセッションが掴んでいるプローブには、ターゲットについて尋ねられません。プローブ自身はディスクリプタから名前が付くので、次の接続イベントまでそのポートのリンクは通常より少なくなります。
- 同じノード名がカーネルから別のデバイスへ再割り当てされたあとでは、古くなったリンクを検出できません。この場合は `cleanup` ではなく、そのポートに対する次の `publish()` で解消されます。
- 2 つのポートが同じボード ID を報告した場合、リンクは 1 つを共有し、最後に公開したものが残ります。古いポートは自分がまだ保持しているリンクを維持し、1 つも保持しなくなった時点で次の cleanup が状態を削除します。
